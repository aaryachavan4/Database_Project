# Part 3: Performance (Person 3)

This folder measures **what data-at-rest encryption costs**: query latency, throughput and table rebuild time on an unencrypted MariaDB server versus an encrypted one that gets its key from HashiCorp Vault.

The findings and numbers are in **[analysis.md](analysis.md)**. The chart is **[charts.png](charts.png)**.

## Files

| File | What it is |
|---|---|
| `benchmark.py` | Runs the benchmark against both servers and writes the CSV results |
| `queries.sql` | Every test query, with the reason it is in the test |
| `analysis.py` | Compares the two servers, computes overhead and 95% confidence intervals, draws `charts.png` |
| `results/baseline_unencrypted.csv` | Summary per query and mode, unencrypted server (mean, median, min, max, stdev, variance, CV, 95% CI, p95, runs) |
| `results/encrypted.csv` | The same for the encrypted server |
| `results/comparison.csv` | Overhead per query with its 95% CI and whether it is significant |
| `results/summary.md` | The comparison tables in Markdown (generated, used in `analysis.md`) |
| `results/raw_*.csv` | Every measured run (one row per server × query × run), so the numbers can be checked |
| `results/environment_*.json` | Server settings, row counts, encryption status and file sizes captured at test time |
| `charts.png` | Visual comparison |
| `analysis.md` | Findings |

## Method (why the comparison is fair)

- **Two servers, same everything except encryption.** Same MariaDB version (13.0.2), same buffer pool, same `innodb_flush_log_at_trx_commit=1`, binary log on in both. The encrypted server adds exactly the settings in `mariadb/hashicorp.cnf` (Vault plugin, `innodb_encrypt_tables=FORCE`, encrypted redo log, temporary files and binlog).
- **Identical data.** 10,000 customers, 50,000 accounts and 1,000,000 transactions, generated by `mariadb/load_data.py`. They were loaded once, copied to the second server and rebuilt on both (`ALTER TABLE … FORCE`, as in `mariadb/encrypted-config.sql`). `CHECKSUM TABLE` was identical on both servers before testing.
- **Measured side by side.** In each run both servers execute the same query with the **same seeded random ids**. The server that goes first alternates every run, so machine noise and caching effects hit both equally.
- **Repeated.** 1 warm-up run (discarded) plus **10 measured runs** per query. Each run repeats the query several times (300× for point lookups, once for 1M-row scans in quick mode). Variance, standard deviation, CV, 95% CI and p95 are calculated across the 10 runs.
- **Significance.** `analysis.py` bootstraps the 10 run means of each server (10,000 resamples) to get a 95% confidence interval for the overhead. If the interval includes 0%, the difference is reported as noise.
- **Writes leave no trace.** Writes run with autocommit, so the time includes the commit (encrypted redo log + binlog write and fsync). Inserted benchmark rows are deleted after each run (not timed), so both servers keep identical data.

### What is measured

| Mode | What it shows |
|---|---|
| `hot` (1 GB buffer pool) | Normal case: the 1M-row data set fits in memory, so pages are decrypted once and then cached |
| `cold` (32 MB buffer pool) | Worst case: most pages are read from disk and **decrypted on every read**; dirty pages are encrypted on every flush |
| `throughput` | Concurrent clients (1 and 8) doing primary-key reads, or single-row insert + commit, for a fixed time |
| `rebuild` | `ALTER TABLE transactions FORCE`, the cost of (re)writing and encrypting all 1M rows |

## How to run it

Requirements: Python 3.9+, plus `pip install pymysql matplotlib numpy` (`faker` too, for loading data).

You need **two** MariaDB servers with the same data: the encrypted one from `mariadb/start.sh` and a plain one.

```bash
export DB_PASSWORD=your_password            # or MYSQL_ROOT_PASSWORD

# 1. Encrypted server: the normal project setup (port 3306)
bash mariadb/start.sh

# 2. Unencrypted server: same MariaDB version, binlog on, no encryption (port 3307)
docker run -d --name mariadb-plain -e MARIADB_ROOT_PASSWORD="$DB_PASSWORD" -p 3307:3306 \
  mariadb:13.0.2 --log-bin=mysql-bin --server-id=1 --innodb-buffer-pool-size=1G

# 3. Copy the same data into it and rebuild both servers' tables identically
docker exec -e MYSQL_PWD="$DB_PASSWORD" mariadb mariadb-dump -uroot --databases encryption_test --single-transaction \
  | docker exec -i -e MYSQL_PWD="$DB_PASSWORD" mariadb-plain mariadb -uroot
docker exec -e MYSQL_PWD="$DB_PASSWORD" mariadb-plain mariadb -uroot encryption_test \
  -e "ALTER TABLE customers FORCE; ALTER TABLE accounts FORCE; ALTER TABLE transactions FORCE;"

# 4. Run (both servers must have the same buffer pool size; the encrypted
#    container uses MariaDB's default unless you add it to hashicorp.cnf)
B="--baseline 127.0.0.1:3307 --encrypted 127.0.0.1:3306"
python performance/benchmark.py --mode hot        $B
python performance/benchmark.py --mode throughput $B
python performance/benchmark.py --mode rebuild    $B
#    restart BOTH servers with innodb_buffer_pool_size=32M, then:
python performance/benchmark.py --mode cold       $B

# 5. Compare and draw the chart
python performance/analysis.py
```

Defaults are `--baseline 127.0.0.1:3306 --encrypted 127.0.0.1:3307`. Useful options: `--runs` (default 10), `--warmup` (1), `--max-slow-reps 1` (quick mode), `--threads 1 8`, `--tp-seconds`, `--tp-rounds`, `--only q2_customer_by_pk …`.

The script checks both servers before it starts. It warns if their row counts differ, if the "encrypted" server has encryption off, or if the baseline has it on.

## Test environment for the committed results

The committed results were produced on a Windows 11 laptop (Intel Core i7-1250U, 10 cores / 12 threads, 16 GB RAM, NVMe SSD), using the official MariaDB 13.0.2 Windows build (which ships the same `hashicorp_key_management` plugin) and Vault 2.2.2 with file storage, set up exactly as `vault/setup.sh` does (KV v2 at `mariadb/`, key `1`, `mariadb-policy` token). Docker was not available on that machine, so the Docker commands above are the equivalent for the team setup. The exact server settings captured during each test are in `results/environment_*.json`.

Results are machine-specific: the **relative** overhead is what carries over, not the absolute milliseconds.
